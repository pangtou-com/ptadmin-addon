# 第三方登录能力协议现状

## 协议定位

第三方登录能力属于 `ptadmin-addon` 的插件能力协议。它负责统一发现和调用 OAuth、OpenID Connect、微信登录、QQ 登录等渠道适配器，不负责直接完成 PTAdmin 用户注册、账号绑定、登录态签发或后台管理员认证。

当前调用链为：

```text
插件注册 auth inject
    -> addon_cap('auth') 发现能力
    -> addon_auth($code, $addonCode) 选择能力
    -> AuthGateway 调用插件处理器
    -> AuthInterface 返回渠道认证结果
```

协议调用结果仍需由宿主业务完成账号识别、绑定冲突处理、用户状态检查、登录态签发和审计记录。不能把 `handleCallback()` 的成功返回直接视为站内用户已经登录。

## 当前已实现能力

- 插件通过 `InjectDefinition` 在 `auth` 分组注册一个或多个第三方认证能力。
- `addon_cap('auth')` 提供已注册能力查询和可选的就绪状态检查。
- `addon_auth()` 和 `Addon::auth()` 提供认证能力网关。
- `AuthInterface` 约定 `getAuthorizeUrl`、`handleCallback`、`getUser`、`refreshToken` 四个动作。
- `AuthGateway` 会检查处理器是否实现 `AuthInterface`，并通过 `supports()` 拒绝插件未声明支持的动作。
- 能力编码发生跨插件重复时，按能力编码调用会失败，调用方可以同时指定插件编码和能力编码消除歧义。

## 当前协议边界

当前实现是渠道适配层，不是完整的第三方登录业务协议。以下职责尚未由协议统一：

- `state` 的生成、服务端存储、有效期、一次性消费和回调比对。
- OpenID Connect 的 `nonce`、`id_token` 校验，以及 OAuth PKCE 的 `code_verifier`、`code_challenge` 传递规则。
- 第三方身份与站内用户的绑定、换绑、解绑和冲突处理。
- 首次登录是否自动注册，以及昵称、头像、邮箱、手机号等资料的可信级别和更新规则。
- 用户禁用、租户、组织、角色、权限、登录日志和审计记录。
- Web Session、API Token 或其他站内登录凭证的签发方式。
- 渠道拒绝授权、授权码失效、令牌换取失败、资料权限不足等标准错误分类。

宿主接入当前协议时必须自行完成上述安全和业务处理，并在调用 `handleCallback()` 前校验本次回调是否对应一个由宿主发起、尚未消费且没有过期的授权事务。

## 已确认的协议缺口

### 固定结构没有运行时约束

`AuthInterface` 和能力接口文档声明了固定输入、固定输出，但当前方法仍直接接收 `InjectPayload` 并返回普通数组。`AuthGateway` 不校验必填字段、字段类型或完整性。

这意味着插件遗漏 `access_token`、`openid`、`meta`、`raw` 等固定字段时仍可通过接口调用，错误会推迟到宿主消费结果时发生。现有测试也只验证了部分字段匹配，不能证明返回结构满足文档约定。

### 授权事务安全责任不明确

当前文档把 `state` 描述为防重放状态值，但协议没有定义由谁生成、保存和比对，也没有要求一次性消费。调用方若只把回调中的 `state` 继续传给插件，不能形成 CSRF 和登录串号防护。

后续协议必须把授权事务视为宿主安全状态，而不是普通渠道透传参数。插件可以参与构造渠道请求，但不能替代宿主对授权事务归属和有效性的验证。

### 默认能力选择不稳定

`addon.defaults.auth` 当前只配置插件编码。一个插件注册多个 `auth` 能力时，默认调用会选择该插件注册的第一个能力；配置不存在或失效时，还会回退到全局发现的第一个能力。

登录入口不应依赖插件扫描顺序。生产调用应显式保存并使用 `addon_code + code` 完整能力引用；默认配置失效时应报告配置错误，不应静默切换登录渠道。

### 可选刷新能力建模矛盾

`refreshToken` 通过 `supports()` 表达为可选动作，但实现 `AuthInterface` 的插件仍必须声明该方法。这个设计会迫使不支持刷新令牌的渠道提供无效占位实现。

后续应将基础登录动作和刷新令牌能力拆分为不同接口，保持“实现了接口就能执行对应动作”的一致语义。

### 尚未形成真实接入闭环

当前工作区没有真实第三方登录插件，也没有宿主业务通过 `Addon::auth()` 完成账号绑定和站内登录。`ptadmin` 中历史用户服务仍保留另一套未完成的 OAuth 调用逻辑，不能作为插件认证协议的宿主实现。

因此，当前协议可以用于插件 SDK 适配和能力发现，但在首个真实渠道与宿主接入完成前，不应标记为完整可用的第三方登录功能。

## 后续演进方向

后续建议以认证协议 v2 的形式收敛，不直接扩大当前普通数组协议：

1. 使用请求对象和结果对象约束四个阶段的固定字段、类型和必填规则。
2. 使用 `addon_code + code` 完整能力引用，移除登录过程中的扫描顺序选择和静默回退。
3. 定义授权事务对象，明确 `state`、有效期、一次性消费、回调地址和发起场景的宿主校验责任。
4. 为 OpenID Connect 和 PKCE 保留受约束的标准字段，不依赖无边界的 `meta` 传递关键安全参数。
5. 将刷新令牌拆为可选接口，并定义标准错误分类。
6. 单独制定宿主账号绑定协议，覆盖首次登录、已绑定、身份冲突、换绑、解绑、禁用用户和审计记录。
7. 通过至少一个真实渠道插件和一个宿主登录流程验证协议，再决定兼容和发布策略。

认证协议 v2 进入实现前，需要先确认目标用户是后台管理员、站点前台用户还是两者都支持。两类用户的账号模型、权限校验和登录凭证不同，不应在渠道适配器中混合处理。

## 涉及范围

后续实现预计涉及：

- `ptadmin-addon`：认证契约、能力声明、能力引用、网关、协议 DTO 和包内测试。
- `ptadmin`：只有在确认后台管理员需要第三方登录时，才增加宿主认证编排、账号绑定和审计能力。
- 具体业务插件：渠道 SDK 调用、配置读取和渠道响应归一化。
- `app.ptadmin.com`：只有后台管理员登录场景成立后，才增加登录入口、回调状态和错误展示。

具体渠道密钥、开放平台差异和业务账号规则不进入 `ptadmin-addon` 公共协议。
